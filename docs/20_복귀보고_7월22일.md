### 발견 1 ★★ 점수를 크게 올릴 방법을 하나 찾았고, 실제로 쓸 수 있는지까지 확인했습니다

**무엇을**: 같은 문제를 난수 씨앗만 바꿔 여러 번 풀고 그중 제일 좋은 답을 내는 전략(best-of-N)이 값어치가 있는지 쟀습니다.

**왜**: 이전에 "서로 다른 두 방식 중 좋은 것 고르기"는 무익하다고 결론이 나 있었습니다. 남은 길은 **같은 방식을 여러 번 돌려 고르기**인데, 이게 되려면 같은 문제의 답이 실행할 때마다 충분히 흔들려야 합니다.

**알아낸 것 (1) — 흔들림이 큽니다**: 같은 문제를 8번 풀렸을 때 **최선과 최악의 차이가 중앙값 0.266**이었습니다. 고를 값어치가 충분합니다.

**알아낸 것 (2) — 그런데 "어느 게 최선인지" 알 수 있나?** 이게 진짜 관문이었습니다.
- 점수의 **40%(Action)**: 시험 문제의 행동 순서는 **우리에게 주어진 입력**이라 로컬에서 정확히 채점할 수 있습니다 → **고를 수 있습니다.**
- 점수의 **60%(DINO·Video)**: 정답 영상이 없어 못 잽니다 → 못 고릅니다.

그러면 "Action만 보고 고르기"가 되는데, **Action만 좇다가 화질을 망쳐 나머지 60%를 잃으면 전체로는 손해**일 수 있습니다. 이걸 우리 모의고사(정답 영상이 있음)에서 검증했습니다.

| 몇 번 뽑나 | 그냥 1번 | **Action 보고 고르기** | 정답 알고 고르기(이론상 최대) |
|---|---|---|---|
| 2번 | 0.644 | 0.628 (**−0.016**) | 0.626 |
| 3번 | 0.644 | 0.621 (**−0.023**) | 0.619 |
| 4번 | 0.644 | 0.618 (**−0.026**) | 0.615 |

**우리가 실제로 할 수 있는 선택이 "정답을 아는 이상적 선택"의 91%를 회수했습니다.** 그리고 걱정했던 부작용이 없었습니다 — 화질(DINO)은 오히려 미세하게 좋아졌고 Video는 그대로였습니다.

**시간은 되나?**: 3번 뽑으려면 문제당 시간이 3배 드는데, 앞서 확인한 묶음 처리(배치) 가속을 쓰면 문제당 14.1초로 **제한(16.7초) 안에 들어옵니다.**

**그래서**: **−0.023은 현재 리더보드 1위(0.27184)와 2위(0.30241)의 격차와 맞먹는 크기입니다.** 다만 지금 당장 쓸 카드는 아닙니다 — 이 기법은 "모델이 만든 영상 중 고르기"라서, 우리 모델(베이스라인)이 아직 정지 영상 전략보다 못하는 지금은 얹어도 소용없습니다. **모델이 정지 영상을 넘어선 뒤 얹는 마지막 한 방**입니다. → [docs/17 §6.5](17_E2_학습전략_초안.md)

### 발견 2 ★ 고쳐야 할 곳을 잘못 찍을 뻔했습니다

**무엇을**: 로봇 팔 관절 6개 중 어느 관절의 예측이 점수를 가장 많이 깎아먹는지 쪼개봤습니다.

**왜**: 점수의 40%가 "로봇이 어떻게 움직였는지 맞히기"(Action 성분)인데, 그 오차 0.588이 6개 관절에 어떻게 나뉘는지 아무도 재본 적이 없었습니다. 어디를 고쳐야 할지 정하려면 이게 먼저입니다.

**알아낸 것**: 데이터를 조사했을 때는 **손목 회전축(wrist_roll)**이 압도적으로 문제로 보였습니다. 학습 데이터와 시험 데이터가 87도나 어긋나 있고, 학습용 데이터셋 128개 중 **100개가 시험에서 실제로 쓰이는 각도 범위를 한 번도 본 적이 없었습니다**. 다른 관절은 전부 90% 이상이 커버하는데 이 관절만 22%였습니다.

그런데 **실제로 점수를 깎는 정도를 재보니 이 관절이 6개 중 꼴찌(6.8%)였습니다.**

| 관절 | 점수 깎는 비중 |
|---|---|
| 어깨 좌우 회전 (shoulder_pan) | **22.8%** |
| 어깨 상하 (shoulder_lift) | 20.3% |
| 팔꿈치 (elbow_flex) | 19.7% |
| 집게 (gripper) | 16.0% |
| 손목 굽힘 (wrist_flex) | 14.4% |
| **손목 회전 (wrist_roll)** | **6.8%** |

**이유**: 채점할 때 각 관절의 오차를 그 관절의 "평소 변동 폭"으로 나눕니다. 손목 회전은 원래 이리저리 많이 도는 관절이라 나누는 값이 크고(62.55), 그래서 87도를 틀려도 점수에는 조금만 반영됩니다. 반대로 어깨 좌우 회전은 나누는 값이 작아서(26.40) **같은 크기의 오차가 2.4배로 증폭**됩니다.

**그래서**: 개선 노력은 **어깨·팔꿈치 관절(합쳐서 62.8%)**에 써야 합니다. 데이터 조사만 보고 정했으면 정반대 방향으로 갈 뻔했습니다. → [docs/17 §3](17_E2_학습전략_초안.md)

### 발견 3 ★ 학습 데이터 고르는 기준이 하나로는 부족합니다

**무엇을**: 학습 데이터 128개가 각각 시험 문제와 얼마나 닮았는지 두 가지 방식으로 순위를 매겼습니다 — ① 장면이 얼마나 비슷해 보이나(겉모습) ② 로봇이 움직이는 방식이 얼마나 비슷한가(동작).

**왜**: 학습 데이터가 103만 장이라 전부 똑같이 쓸 수 없고, 시험과 닮은 것에 힘을 실어야 합니다. 그러려면 "닮음"을 수치로 재야 합니다.

**알아낸 것**: **두 순위가 서로 거의 무관합니다** (순위 상관 +0.04, 0이면 완전 무관). 양쪽 모두 상위 40위 안에 드는 데이터셋은 128개 중 **12개뿐**이었습니다.

> 가장 극적인 사례: `Loki0929/so100_duck`은 겉모습으로는 **4위**인데 동작으로는 **127위**(끝에서 두 번째)입니다. 기존 팀 문서(docs/10)가 겉모습만 보고 "시험과 닮은 데이터"로 지목했던 것이라, 그대로 썼으면 동작 학습에는 해로운 데이터를 우대할 뻔했습니다.

**그리고 더 중요한 것 — 겉모습 순위는 모델이 어디서 실패할지 아예 못 맞혔습니다.**

시험 문제 216개는 촬영 환경 두 곳에서 나왔습니다. A 환경 154개(71%), B 환경 62개(29%). 겉모습으로 보면 **B 환경 쪽에 닮은 학습 데이터가 훨씬 많습니다**(상위 10개 중 8개). 그래서 저는 처음에 "다수인 A가 방치될 위험"이라고 적었습니다.

**실제로 재보니 정반대였습니다.**

| | A 환경 (154개, 71%) | B 환경 (62개, 29%) |
|---|---|---|
| 닮은 학습 데이터 | 적음 | 많음 |
| **실제 모델 성적** | **0.508** | **0.787 (훨씬 나쁨)** |

닮은 데이터가 더 많은 B에서 모델이 훨씬 못합니다. B는 문제의 29%인데 전체 오차의 **38%**를 냅니다.

혹시 다른 이유일까 싶어 두 가지를 확인하고 **둘 다 기각**했습니다: ① "B의 동작이 더 크고 어려운가?" → 동작량이 A 167.2 / B 167.7로 사실상 같음 ② "채점기가 B 화면에서 오작동하나?" → 정지 영상 전략은 두 환경에서 성적이 같음.

**그래서 생성된 영상을 직접 열어봤습니다. 실패의 형태가 예상과 달랐습니다.**

모델은 **틀린 동작을 그리는 게 아니라, 동작을 아예 그려내지 못하고 뭉개고 있었습니다.** 프레임이 진행될수록 로봇 팔이 흐릿한 얼룩으로 녹아버립니다. 수치로 재보니:

| | A 환경 | B 환경 |
|---|---|---|
| 마지막 장면이 유지한 선명도 (첫 장면 대비) | 66.6% | **40.5%** |

**B가 1.6배 더 심하게 뭉개집니다.** 그리고 덜 뭉개진 문제일수록 점수가 좋았습니다(상관 −0.339).

**이게 큰 그림을 설명합니다** — 왜 "아무것도 안 움직인다"는 정지 영상 전략이 실제 모델을 이기는지. 선명한 정지 화면이 뭉개진 영상보다 세 채점 항목 **전부**에서 낫기 때문입니다. (화질 항목에서는 정지 영상이 3.7배 좋습니다.)

**결론**: 현재 베이스라인 모델(1,100만 개 파라미터의 작은 모델)은 **개선의 출발점으로 부적합합니다.** 다음 단계에서 제대로 된 영상 생성 모델로 갈아타야 한다는 팀 계획이 데이터로 뒷받침됩니다.

B가 더 심한 이유는 **B가 옆에서 위로 올려다보는 각도인데 학습 데이터 대부분은 위에서 내려다보는 각도**이기 때문으로 보입니다(추정). 겉모습 비교는 "무엇이 찍혔나"는 봐도 **"어느 각도에서 찍혔나"는 못 본 것**입니다.

**그래서**: 데이터 선별을 겉모습 순위로 하면 안 됩니다. **실제로 어디서 틀리는지 측정한 값**을 기준으로 삼고, 유사도 순위는 후보를 좁히는 보조로만 써야 합니다. 최우선 개선 대상은 **B 환경의 큰 관절 동작**입니다. → [docs/17 §1.3](17_E2_학습전략_초안.md)

*(이 정정은 제가 앞서 쓴 문서 `docs/19`에도 정정 블록으로 달아뒀습니다. 나중에 그 문서만 읽는 사람이 낡은 결론을 그대로 믿으면 안 되기 때문입니다.)*

### 발견 4 ★ 같은 설정으로 돌려도 같은 영상이 안 나옵니다

**무엇을**: 어제 Kaggle 서버에서 낸 결과를 이 서버에서 똑같은 설정(같은 난수 씨앗, 같은 단계 수)으로 재현해봤습니다.

**왜**: 두 서버의 결과가 같아야 실험 비교가 의미를 갖습니다. 팀 규칙에도 "재현 실험은 하드웨어 무관하니 카드 자유"라고 적혀 있어서, 이게 사실인지 확인이 필요했습니다.

**알아낸 것**: 결과가 **부분적으로만** 재현됩니다.

- **전체 평균은 비슷**: 0.5801(Kaggle) vs 0.5877(여기), 차이 +0.0076
- **개별 문제는 전혀 다름**: 216개 중 **141개가 크게 다르고**, 문제별 상관관계가 0.77에 그침
- 하지만 **분포의 모양은 거의 같음** (표준편차 0.2266 vs 0.2261, 사분위수 일치)

즉 영상 생성 과정이 **수치적으로 카오스적**입니다 — 아주 작은 계산 차이(하드웨어·라이브러리 버전)가 50단계를 거치며 증폭돼 다른 영상이 됩니다.

**추가 확인**: **한 번에 처리하는 묶음 크기(배치)를 바꿔도 8개 중 8개가 전부 다른 영상**이 나왔습니다. 속도를 올리려고 배치를 키우면 결과가 바뀝니다.

**그래서**:
- 실험 비교는 **평균값으로만** 하고, 개별 문제 단위 비교는 하지 말 것. 비교 해상도는 약 ±0.01입니다.
- **최종 제출물은 반드시 한 서버·한 설정·중단 없이 한 번에** 생성해야 합니다. (팀 규칙에 이미 있는 조항이고, 이번 측정이 그 근거를 강화합니다)
- **팀 규칙은 고칠 필요가 없습니다(확인 완료).** 처음엔 규칙의 "Δ0.0003이라 카드 자유"와 제 측정(Δ0.0076)이 25배 차이나 보였는데, 이후 난수 씨앗만 바꿔 8번 돌려보니 **씨앗을 바꾼 것만으로 생기는 흔들림이 (216문제 환산) 0.0077**이었습니다. 제가 관측한 하드웨어 간 차이 0.0076과 **사실상 같은 값**입니다. 즉 다른 컴퓨터에서 돌린 차이가 같은 컴퓨터에서 씨앗만 바꾼 것과 구별되지 않습니다. 규칙은 집계 수준에서 유효합니다.

### 발견 5 이 서버가 예상보다 훨씬 쓸만합니다

**무엇을**: 채점과 생성을 이 서버에서 돌려 속도와 정확도를 쟀습니다.

**알아낸 것**:
- **채점은 완벽하게 재현됩니다** — Kaggle 결과와 소수점 16자리까지 일치(생성과 대조적). 속도는 2배. **이제 채점에 Kaggle이 전혀 필요 없습니다** (기존에는 Kaggle 사용량 한도와 네트워크 차단에 묶여 있었습니다).
- **생성 속도 10.4초/문제** — 대회 제한이 16.7초/문제인데, Kaggle에서는 20.7초로 **초과**했었습니다. 이 서버는 여유롭게 들어옵니다.
- 216문제 전량 생성이 **50.5분** (모델 읽는 시간 포함), 대회 한도 1시간 대비 9.5분 여유.
- 서버 사양이 인수인계 메모와 달랐습니다: 4코어/48GB가 아니라 **40코어/251GB**입니다. 그래서 데이터 분석을 32개 프로세스로 병렬 처리해 128개 데이터셋 전수 조사를 60초에 끝냈습니다.

- **다음 단계 후보 모델(Wan2.2-5B)도 올라갑니다** — 메모리 19.9GB로 여유 11.8GB. 라이선스도 Apache-2.0이라 대회 조건을 만족합니다. (적재 확인까지만 했습니다 — 실제 추론과 실험 설계는 팀원 영역입니다)

**그래서**: 기존에 Kaggle에서 하던 작업 상당수를 여기로 옮길 수 있습니다. **대회 제한 시간 안에서 단계 수를 줄일 이유도 사라졌습니다** (Kaggle 제약 때문에 했던 최적화입니다).

**추가로 찾은 함정 하나**: 이 GPU에서 `bf16`이라는 숫자 형식을 쓰면 안 됩니다. PyTorch가 "지원한다"고 답하지만 실제로는 흉내만 내는 것이라, 측정해보니 **fp16보다 8.4배 느리고 fp32보다도 느렸습니다.** 프로그램이 "지원 여부"만 확인하고 켜면 8배 느려집니다. 팀 보드에 공유해뒀습니다.

### 발견 6 환경 구축에 숨은 구멍이 5개 있었습니다

**무엇을**: 이 서버에서 처음으로 "영상 생성"을 돌려봤습니다.

**왜**: 지금까지 생성은 Kaggle에서만 했습니다. 팀 규칙은 "`uv.lock` 파일 하나로 어느 서버든 같은 환경이 재현된다"고 하는데, 실제로는 **채점 경로만** 재현되고 있었습니다.

**알아낸 것**: 생성에 필요한 부품 5개가 빠져 있었습니다(`opencv`, `transformers`, `open_clip`, `requests`, `kornia`). Kaggle 이미지에는 기본 탑재라 그동안 드러나지 않았습니다. 특히 `kornia`는 **대회 주최측이 준 목록에도 없습니다** (주최측 목록의 두 번째 누락 버그입니다).

환경 함정도 2개 찾았습니다:
1. `uv run` 명령을 쓸 때마다 환경을 재정리하면서 수동 설치한 부품을 **지워버립니다**.
2. 이 서버에는 다른 파이썬 환경이 함께 잡혀 있어서, 설치 명령이 엉뚱한 곳에 설치됩니다 — **설치는 성공했다고 나오는데 실행하면 없다고 나오는** 형태라 원인 찾기가 까다롭습니다.

**그래서**: 전부 고쳐서 커밋했고 함정은 스크립트 주석에 남겼습니다. 이제 새 서버에서도 스크립트 두 개로 환경이 완성됩니다.

### 발견 7 공짜로 주울 수 있는 작은 점수가 있습니다

**무엇을**: 영상 압축 설정이 점수에 주는 영향을 쟀습니다.

**왜**: 우리가 제출하는 건 영상이 아니라 **영상에서 뽑아낸 숫자표**입니다. 그러니 영상 압축 설정은 전적으로 우리 마음이고, 압축 때문에 잃는 점수는 스스로 입히는 손해입니다.

**알아낸 것**: 압축 품질 설정(CRF)을 최고에서 최저까지 바꿔도 점수 차이는 +0.0003뿐인데, **압축을 아예 안 한 것과 최고 품질로 압축한 것의 차이가 +0.0007로 더 컸습니다.** 범인은 품질 설정이 아니라 **색 정보를 절반으로 줄여 저장하는 방식(yuv420p)**이었습니다. 색을 그대로 저장하는 방식(yuv444p)으로 바꾸니 손실의 68%가 회복됐고 파일은 8%만 커졌습니다.

**실제 영상으로 재측정했더니 효과가 10배 컸습니다.** 위 측정은 "정지 영상"으로 한 것인데, 정지 영상은 16장이 전부 같아서 압축이 거의 무손실이 되는 특수한 경우였습니다. 실제로 움직이는 생성 영상 80개로 다시 재니:

| 저장 방식 | 점수 손실 |
|---|---|
| yuv420p (현재 방식, 최고 품질로 해도) | **+0.002** |
| yuv444p (색 정보 유지) | **거의 0** |

**그래서**: 총점 기여 약 **0.0008**, 비용은 파일 크기 8% 증가뿐입니다. 고칠 곳도 한 줄로 특정했습니다. 다만 대회 주최측 코드 계열 파일이라 제가 단독으로 바꾸지 않고 팀원 판단을 요청해뒀습니다. → [docs/17 §6](17_E2_학습전략_초안.md)

### 발견 8 기존 문서의 오류 2건

1. **팀 문서(docs/05)가 "이상한 데이터셋"으로 지목한 `liyitenga/so100_bi_giveme5`는 학습 데이터에 아예 없습니다.** 실제로 카메라 이름이 다른 데이터셋은 `triton7777/so100_dataset_mix`였고, 직접 영상을 열어 확인해보니 **평범한 작업대 화면**이라 제외할 이유가 없었습니다.
2. **제 앞 세션의 인수인계 메모가 서버 사양을 잘못 적었습니다** (발견 4 참조).

또 하나, 이번에 넘겨받은 5시간 계획서에는 **이미 끝난 작업(E1 스텝 스윕)이 다시 들어 있었습니다.** 어제 Kaggle에서 완료해 문서에 기록까지 돼 있는 작업이라, 그대로 했으면 5시간을 이미 나온 숫자를 다시 뽑는 데 썼을 것입니다. 대신 아직 안 해본 **교차 재현 검증**으로 바꿔 진행했고, 그 판단에서 발견 3이 나왔습니다.

## 3. 용어집

| 용어 | 뜻 |
|---|---|
| **eval (평가 데이터)** | 주최측이 정답을 숨긴 채 준 216개 문제. 우리 점수는 이걸로 매겨진다. |
| **train (학습 데이터)** | 정답이 있는 연습 문제. 128개 데이터셋, 약 103만 장의 사진. |
| **홀드아웃(holdout)** | train에서 일부러 떼어놓고 학습에 안 쓰는 몫. 우리끼리 채점해보는 모의고사. |
| **베이스라인(baseline)** | 주최측이 준 기본 모델. 이걸 이겨야 의미가 있다. |
| **정적 예측(static)** | 첫 사진을 16번 반복해 "아무것도 안 움직인다"고 답하는 전략. 놀랍게도 현재 우리 최고점. |
| **MAE (Mean Absolute Error)** | 평균 절대 오차. 예측과 정답의 차이를 평균한 값. **낮을수록 좋다.** |
| **DINO** | 사진을 숫자 벡터로 바꿔주는 AI 모델. 두 사진이 얼마나 닮았는지 재는 데 쓴다. |
| **코사인 유사도** | 두 벡터가 이루는 각도로 재는 닮음 정도. 1이면 완전히 같은 방향. |
| **에피소드(episode)** | 로봇이 과제를 한 번 수행한 녹화 1건. |
| **프레임(frame)** | 영상의 낱장 사진. |
| **fps (frames per second)** | 초당 프레임 수. 영상이 얼마나 촘촘히 찍혔는지. |
| **코덱(codec)** | 영상 압축 방식. av1, h264 등. |
| **CRF (Constant Rate Factor)** | 영상 압축 품질 조절값. 낮을수록 고품질·큰 파일. |
| **yuv420p / yuv444p** | 영상의 색 저장 방식. 420은 색 정보를 절반으로 줄여 저장(용량 절약), 444는 그대로 저장. |
| **no-op (no operation)** | 켜도 아무 효과가 없는 설정. |
| **seed (난수 씨앗)** | AI가 무작위로 뭔가 할 때 쓰는 초기값. 같으면 같은 결과가 나온다. |
| **best-of-N** | 같은 문제를 N번 풀고 그중 제일 좋은 답을 내는 전략. |
| **체크포인트(checkpoint, ckpt)** | 학습된 AI 모델을 파일로 저장한 것. |
| **uv.lock** | 프로그램이 쓰는 부품(라이브러리)의 버전을 정확히 못박아둔 파일. 다른 컴퓨터에서도 똑같은 환경을 만들기 위한 것. |
| **editable 설치** | 라이브러리를 복사하지 않고 원본 폴더를 직접 참조하게 설치하는 방식. |
| **큐레이션(curation)** | 학습에 쓸 데이터를 골라내는 일. |
| **정규화(normalization)** | 숫자들의 크기·기준을 맞춰주는 처리. |
| **어안 렌즈(fisheye)** | 시야가 아주 넓은 대신 화면이 둥글게 휘어 보이는 렌즈. |

## 4. 남은 일과 제안

### 4.1 복귀 후 결정이 필요한 것

**① 팀원(T) 승인이 필요한 기술 제안 5건** — [docs/17](17_E2_학습전략_초안.md) §7에 정리했습니다. 요약하면:
- 학습에서 뺄 데이터 목록 확정
- `Chojins` 체스 데이터(전체의 12.7%) 비중을 줄일지, 줄인다면 얼마나
- 데이터 선별을 촬영 환경별 할당량으로 할지
- 손목 회전축 보정을 넣을지 (학습 코드는 T 영역)
- 최종 제출물 생성 설정을 어떻게 고정할지

**② 팀 규칙 한 줄 재검토 요청** — 룰북 §6은 *"재현 실험은 하드웨어 무관하니 카드 자유"*라고 적혀 있는데, 근거로 든 수치(Δ0.0003)와 제 측정(Δ0.0076)이 25배 차이납니다. 다만 발견 3에서 적었듯 이건 **난수 흔들림 범위 안**일 가능성이 큽니다(Phase 3 결과로 판정). 판정 결과를 보고 개정 제안 여부를 정하면 됩니다. BOARD에 확인 요청으로 올려뒀습니다.

**③ 제가 재량으로 바꾼 계획 1건** — 넘겨받은 5시간 계획서의 D·E·F 단계(E1 스텝 스윕 재실행)는 **어제 이미 완료된 작업**이었습니다. 그대로 했으면 5시간을 이미 나온 숫자를 다시 뽑는 데 썼을 것이라, 아직 안 해본 **교차 재현 검증**으로 바꿔 진행했습니다. 이 판단이 맞았는지 확인해 주세요. (결과적으로 발견 3이 여기서 나왔습니다)

### 4.2 제가 다음에 할 수 있는 일 (지시 주시면)

- **셋업 B 실패 원인 규명** — 발견 2에서 나온 가장 큰 실마리입니다. 베이스라인이 측면 상향 뷰에서 왜 못하는지 파고들면 개선 방향이 나옵니다.
- **Wan2.2 모델 적재 시험** — 다음 단계(E2)에서 쓸 후보 모델이 이 서버에 올라가는지 확인. 가중치는 내려받는 중입니다. (라이선스는 Apache-2.0으로 대회 조건 충족 확인)
- **`yuv444p` 적용 후 전체 파이프라인 재검증** — 발견 6의 공짜 개선을 실제로 적용해 끝까지 확인.
- **동작 유사도 기반 큐레이션 시제품** — 실제로 데이터를 골라 학습에 넣었을 때 효과가 있는지 A/B 확인.

### 4.3 제출은 하지 않았습니다

계획서 제약대로 **대회 제출은 한 건도 하지 않았습니다.** 팀원 영역(학습 코드, Kaggle 노트북, W2 설계)도 건드리지 않았고, 공용 파일(`results/`, `LOG.md`, `BOARD.md`)은 기존 줄을 고치지 않고 **덧붙이기만** 했습니다.

한 가지 예외적 판단: `docs/19`(제가 이번에 쓴 문서)에는 **정정 블록**을 달았습니다. 그 문서의 결론이 이후 실측으로 뒤집혔는데, 낡은 결론만 읽고 판단하는 사람이 생기면 안 되기 때문입니다. 원래 서술은 지우지 않고 그대로 뒀습니다.
