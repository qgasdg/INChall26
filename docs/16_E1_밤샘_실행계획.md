# E1 밤샘 실행 계획 (2026-07-19 야간, Y 클로드 자율 실행)

> 착수 선언 완료([슬랙](https://inchall26.slack.com/archives/C0BJ7PWLLN6/p1784393370046249), 7/19). 근거: [15_E1_분담_제안.md](15_E1_분담_제안.md)(T 승인) + [14 §4 재앵커](14_홀드아웃_v2_절차.md). 실행자 = Y측 클로드 백그라운드 에이전트, 사용자 취침 중 자율 진행.

## 목표 (아침까지 산출물)
1. **E1 스텝-품질-시간 곡선**: 스텝 수 50/30/20/12 × eval 216 생성 + 킷 Action MAE + 샘플당 걸린 시간 실측 → 샘플당 16.7초 예산 대비 얼마나 줄일 수 있나 곡선.
2. **홀드아웃 v2 재앵커(기준점 다시 재기)**: v2 처음 보는 셋 162개(사촌 80+일반 82)에서 정적·베이스라인(50스텝)의 DINO+Video 다시 측정 → 원장 기준행.
3. 원장([local_lb.csv](../results/local_lb.csv)) 행 추가 + LOG + 슬랙 완료 보고.

## 사전 확정 사항 (재조사 불필요)
- 생성 스크립트 = `open/baseline/challenge_kit/scripts/inference/generate_baseline_videos.py`, `--ddim-steps` 오버라이드 지원. eval config의 ddim_kwargs: steps 50, **uncond_scale 1.0(CFG 봉인 상태), guidance_rescale 0.7**, uniform_trailing, eta 1.0.
- **홀드아웃 생성 트릭**: challenge 입력 포맷 = `images/<id>.png`(첫 프레임) + `actions/<id>.npy`(16×6) → v2 unseen 샘플을 이 포맷으로 로컬 변환(episode_io, 윈도우 = start부터 16프레임)하면 생성 스크립트 **무수정 재사용**.
- Kaggle: 계정 qgasdg, `.venv/bin/kaggle`, **push 시 `--accelerator NvidiaTeslaT4` 필수**, 마운트 `/kaggle/input/datasets/qgasdg/<slug>/`, pip 레시피 = 이전 커널(`inchall26-static-csv`) 그대로(numpy<2 최후 강제). 쿼터 잔여 29.88h.
- 기존 dataset `inchall26-static-bundle`(146MB) = submission_kit + data/eval. 신규 업로드 필요분: challenge_kit 코드+ckpt(84MB), action stats json, unseen 4개 데이터셋 원본(~108MB), 변환된 challenge 포맷 입력, local_eval 채점 코드.

## 실행 단계
| 단계 | 내용 | 예상 |
|---|---|---|
| P0 로컬 준비 | v2 unseen 162 → challenge 포맷 변환 · score.py v2 대응(--holdout 인자, start 윈도우, v2 티어명) · `inchall26-e1-bundle` 데이터셋 업로드(~300MB) | ~1h |
| P1 스윕 커널 | 커널 1개에서 4 config 순차: 생성(타이밍 실측) → 킷 추출 → Action MAE vs GT npy. 산출 = 곡선 CSV + 로그 | ~5h (config당 ~75분) |
| P2 재앵커 커널 | v2 unseen 162 베이스라인 생성(step 50) + 정적, D+V 채점(in-kernel) | ~2h |
| P3 정리 | 출력 회수 → local_lb.csv 행 추가(exp-02~) · LOG · 본 문서에 결과 추기 · 슬랙 보고 · 커밋/푸시 | ~30m |

## 판단 규칙 (에이전트 재량 범위)
- P1·P2는 커널 분리(세션 한도 회피). 동시 실행 불가 시 P1 먼저(스윕이 주 목표).
- 채점 모델(DINO 등)이 커널에서 다운로드 필요하면 kernel-metadata `enable_internet: true` 허용. 불가 시 가중치를 번들에 동봉.
- guidance_rescale 스윕은 **시간 남으면**: CFG 1.0이라 no-op 가능성 — step 20에서 rescale 0.0 vs 0.7 한 쌍만 실측해 no-op 여부 판정.
- 실패 시 손절: 같은 원인 3회 실패면 해당 단계 보류하고 결과·원인만 기록 (쿼터 낭비 금지).
- 산출물 회수 최우선(룰북 §5) — 커널 종료 전 output 확인, 영상 원본은 회수 말고 점수·CSV만.

## 제약 (룰북 준수)
- 제출 없음 (E1 정의). `results/` CSV는 append-only. T 영역(Kaggle 노트북 = T 소유는 T의 것만 — 내 커널은 별도 slug) 불가침.
- 작업 중 간간이 슬랙 확인(§8), 완료·중단 시 슬랙 보고.

## 결과 (2026-07-19 4차 시도 — P0~P3 전 단계 완주)

> 실행: Y측 클로드 원격 에이전트 (네트워크 정책 조정된 환경). Kaggle GPU 소모 7.2h (P1 스윕 5.8h + P2 재앵커 1.1h + 초기 실패 3회 0.2h). 원장 exp-02~06.

### 1. 스텝-품질-시간 곡선 (eval 216, T4, seed 0, batch 1)
| ddim_steps | Action MAE (킷 실측) | 샘플당 생성(중앙값) | 216개 총 생성 |
|---|---|---|---|
| 50 (기준) | **0.5801** | 20.66s | 75.9min |
| 30 | 0.5864 (+0.0063) | 18.23s | 66.8min |
| 20 | 0.5933 (+0.0132) | 17.15s | 63.1min |
| 12 | 0.6016 (+0.0215) | 16.33s | 59.9min |

- **50스텝 = T의 베이스라인 재현 확인**: MAE 0.5801 vs T 실측 0.579 (+0.001, 환경 차이 수준).
- **★핵심 발견 — 시간은 고정 간접비용(오버헤드)이 지배**: 직선으로 맞춰보면 샘플당 **고정 ~15.0초 + 스텝당 0.114초**. 스텝을 50→12로 76% 줄여도 시간은 21%밖에 안 준다. 잡음 걷어내는 반복이 아니라 모델 로드·인코딩(CLIP/VAE)·디코드·mp4 저장이 병목 → **추론 최적화(E8)의 진짜 레버는 스텝 감축이 아니라 배치 병렬·전처리 파이프라인** (한 번에 1개 기준 실측이므로 배치가 1순위 후보).
- 품질 손실은 완만하고 일정 방향 (12스텝에도 +0.022). 어차피 베이스라인 MAE(0.58+)는 정적(0.4283)보다 나쁘므로 이 곡선의 가치는 점수 자체가 아니라 **방법론·시간 모델**.
- 샘플당 16.7초 예산: T4에서는 12스텝만 턱걸이(16.33초). 단 규칙 기준 하드웨어(PRO 6000)는 T4보다 빠르므로 곡선의 형태(고정비가 지배)는 그대로 옮겨간다는 결론.

### 2. guidance_rescale 스윕 판정 — **효과 없음(no-op) 확정 (훑어볼 필요 없음)**
- 20스텝에서 rescale 0.7 vs 0.0 각각 216개 생성 → **mp4 지문(md5) 216/216 바이트까지 동일**. CFG가 1.0으로 봉인된 상태에선 guidance_rescale이 코드에 아예 안 들어감을 실증. E1 손잡이에서 제거.
- 덤: 같은 seed로 재실행해도 바이트까지 동일 → **생성 파이프라인이 완전히 결정론(매번 같은 결과)임 재확인** (η=0 발견과 앞뒤 맞음).

### 3. 홀드아웃 v2 재앵커 (unseen 162 = 사촌 80 + 일반 82)
| 기준행 | DINO(pf) | Video | Action(참고) | 비고 |
|---|---|---|---|---|
| 정적 (exp-02) | **0.1487** | **0.0848** | 1.1195 | 사촌 D 0.1430/V 0.0719 · 일반 D 0.1543/V 0.0973 |
| 베이스라인 s50 (exp-03) | 0.5534 | 0.2195 | 1.0318 | 사촌 D 0.5479/V 0.2020 · 일반 D 0.5588/V 0.2365 |

- v2에서도 **정적이 DINO+Video 압도** (합산 0.234 vs 0.773) — "베이스라인은 정적을 못 이긴다" 결론이 v2 기준으로도 성립. 이후 원장의 홀드아웃 수치는 이 두 행이 기준 (룰북 §2 수치 정합).
- Action(참고)은 정적 1.12 > 베이스라인 1.03으로 역전 — 추출기가 train 도메인에선 못 믿는다는 기존 결론(08) 재확인. 정본은 여전히 eval 216 킷 실측.
- v2 생성 시간 샘플당 19.34초 — P1의 20.66초와 5% 차 (T4 카드 개체 차이), T의 18.87초와도 정합.

### 4. 실행 기록·산출물
- Kaggle 자산: dataset `inchall26-e1-bundle`(199MB: challenge_kit+ckpt, v2 unseen 원본 4개, 변환 입력 162, local_eval) / 커널 `inchall26-e1-sweep`(5.8h), `inchall26-e1-reanchor`(1.1h), `inchall26-e1-fetch`(CPU 회수용). 커널 코드는 repo `scripts/kaggle/`에 보존.
- 산출물: 원장 exp-02~06 + `results/exp-0N_*_per_sample.csv` 6종 + `results/e1_sweep_summary.csv` + `results/e1_timing.json` + `results/reanchor_v2_summary.json`. **features CSV 4종(각 27.8MB, 216×3성분) 포함 전 산출물은 egress 개방 후 전량 회수 완료 → Kaggle dataset `qgasdg/inchall26-e1-results`(107MB, sweep/+reanchor/)에 영구 보존** (대용량이라 repo 금지 — 룰북 §5). 무결성: Action 평균이 원장 수치와 정확 일치, 로그 경유 회수본과 바이트 동일.
- 초기 실패 3회(각 ~2분, 셋업 단계): ① `open_clip.__version__` 부재 ② HF 캐시 상대 심링크를 하드링크해 backbone 경로 깨짐 ③ 새 커널 이미지(torch 2.10/pl 2.6.5/hf_hub 1.x — **docker_image 핀은 무시됨**)에서 `HfFolder` 제거 → ldwma 임포트 실패, 원격 경로 전용이라 복사본에 호환 셔틀 패치. 이후 `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1` 선제 설정(torch≥2.6 기본값 변화).
- 이 환경 특이: kaggleusercontent.com(출력 파일 다운로드 호스트)이 바깥 통신(egress) 비허용 → **CPU 회수 커널로 로그를 경유해 회수**하는 패턴 확립 (300KB 이하 텍스트 산출물에 유효). 이후 사용자가 바깥 통신 전체 개방 → 직접 다운로드로 잔여분 회수·검증 완료.
- P1 실측이 계획(~5h)보다 긴 6h10m이었던 이유: 위 고정 오버헤드로 저스텝 config가 예상만큼 빨라지지 않음 + config당 모델 재로드(~1.5min) + 킷 채점 4.3min×4 (probe는 md5 동일이라 채점 생략).
